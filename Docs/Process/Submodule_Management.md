# 子仓库（Submodule）管理规范

> 适用：本项目"主仓 + 子模块"的仓库架构。主仓承载变更不频繁的资产（硬件/文档/测试/发布/工具），代码工程（固件/软件）以子模块形式独立管理。

## 1. 仓库拓扑

```
产品主仓（单仓库）
├── Hardware/  Test/  Docs/  Release/  Tools/   ← 主仓资产
├── .gitmodules / .gitignore / .gitattributes / LICENSE ...
├── Firmware/                    ← 子模块：固件仓库
│   └── （固件仓内部）vendor 子模块：HAL/CMSIS/RTOS/中间件（只读）
├── Software/PC_Software/        ← 子模块：电脑端应用仓库
├── Software/Mobile_Software/    ← 子模块：移动端应用仓库
└── Software/Server/             ← 子模块：云端工程（按需）
```

## 2. 归属判据

| 资产 | 归属 | 理由 |
|------|------|------|
| 硬件设计/文档/测试/发布/工具 | 主仓 | 变更不频繁，子模块指针维护成本按变更次数计，不值得拆 |
| 固件源码工程 | 子仓 | 变更频繁、独立构建/发布 |
| 电脑端/移动端/云端工程 | 子仓 | 同上 |
| HAL/CMSIS/RTOS/中间件 | 固件仓内 vendor 子模块 | 依赖管理，升级 = 改指针 |

## 3. 日常开发流程

1. **克隆**：`git clone --recursive <主仓>`（vendor 嵌套子模块一并拉取）；
2. **进入子仓先切分支**：子模块默认 detached HEAD，进入后立即 `git checkout <feature/xxx>`；
3. **正常开发**：在子仓内提交、推送子仓，主仓不感知；
4. **主仓指针更新只在集成/发布时**：`git submodule update --remote <路径>` 或手动指向目标 commit，然后在主仓提交指针变化；
5. **禁止**：在主仓内直接修改子仓代码（Git 会拦截），子仓代码只在子仓内改。

## 4. 版本对齐（核心机制）

- **指针即对齐锚点**：主仓的 commit/tag 会冻结所有子模块指针（精确到 commit）；
- **发布**：`Release/vX.Y.Z` tag 打在主仓 = 同时冻结当时固件/软件的精确版本；
- **release_note 必列**：各子仓 tag/commit + 硬件版本 + 固件 SHA256；
- **追溯链**：Release tag → 主仓 commit → 子模块指针 → 子仓 commit → 源码。

## 5. CI 与一致性校验

- **各子仓独立 CI**：固件构建/单测、软件构建/单测，各自跑；
- **主仓 CI**：文档检查 + **指针一致性校验**（Release 记录与实际 .gitmodules 指针比对，防止"忘了提交指针更新"导致的集成版本漂移）+ Release 打包；
- 发布流程含 checklist：指针已提交、release_note 完整、tag 已打。

## 6. 跨仓联改（无原子性的对策）

- **协议变更流程**：先在主仓 `Docs/Design/Protocol/` 修订协议并定版本号 → 各端（固件/PC/移动端）在各自子仓实现 → release_note 记录对应关系；
- **一个发布周期内统一集成**：禁止跨仓"半提交"（一端改了另一端没改就发版）；
- 同一版本号的协议在 release_note 中必须同时出现各端实现记录。

## 7. 文档归属

- **主仓 `Docs/`**：跨端绑定文档（需求、系统设计、协议、认证、用户手册、管理类归档）+ **全仓文档总索引**（`Docs/README.md`，列主仓与各子仓的文档入口）；
- **子仓内 `Docs/`**：仅该工程专属文档（架构、模块设计、单测方案），随代码仓变更原子提交；
- 判据：文档的"变更主体"是谁就跟着谁走；查文档一律从主仓总索引出发。

## 8. 拆仓与合并

- **拆仓触发条件**（满足其一）：软件端独立发布节奏、团队权限隔离需求、多产品线共享平台代码；
- **合并回主仓**：耦合变紧、变更节奏趋同时；
- **对齐方式**：
  - 指针对齐（默认）：主仓 submodule 固定指针，强一致；
  - 引用对齐：各仓独立打 tag，release_note 记录三方 tag，弱一致但简单，适合独立节奏的软件仓。

## 9. 常见坑

| 坑 | 后果 | 对策 |
|----|------|------|
| 改了子仓代码忘了 push 子仓 | 主仓指针指向未推送的 commit，他人克隆失败 | 发布前检查子仓 `git status`/push 状态 |
| 子模块 detached HEAD 直接提交 | 提交悬空，容易丢 | 进入子仓先 checkout 分支 |
| 忘了提交主仓指针更新 | Release 记录与实际代码漂移 | 主仓 CI 指针一致性校验 |
| 频繁切分支 | LFS 大文件（PCB/STEP）反复传输 | 分支少而短，避免长期并行大分支 |
| 嵌套子模块忘记 `--recursive` | 克隆后 vendor 缺失编译失败 | 统一用 `git clone --recursive` |
